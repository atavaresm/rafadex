# Info Page ("Sobre o Pokédex") Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the feature from `docs/superpowers/specs/2026-08-11-info-page-design.md`: a new ℹ️ button next to the search icon on Home, opening a new `#info` full-screen route that tells the app's origin story and links to the public GitHub repo.

**Architecture:** One new button in the existing `toolRow` (`app.js`'s `renderHome()`), one new route branch in `renderRoute()`, one new render function (`renderInfo()`) following the exact same full-screen-route pattern as `renderGame()` (`topbar()` for the header/back button, content appended to `elApp`), and one new CSS block for the content card. No data pipeline, no new files besides the plan/spec docs.

**Tech Stack:** Vanilla HTML/CSS/JS (unchanged), no framework/bundler.

## Global Constraints

- Spec: `docs/superpowers/specs/2026-08-11-info-page-design.md`.
- The approved copy (heading + two paragraphs + link label) is reproduced verbatim in Task 1 below — do not paraphrase or shorten it.
- GitHub link, exact: `https://github.com/atavaresm/rafadex`, opens in a new tab (`target="_blank" rel="noopener"`).
- Icon: ℹ️ emoji, reusing the existing `.gear` CSS class (a generic 44px circular icon-button style, not specific to the downloads panel despite the name) — do not invent a new icon class for this.
- Route: `#info`, using the existing full-screen-route pattern (`topbar()` + content in `elApp`), **not** the small in-Home panel pattern used by the gear/search buttons (`renderParentPanel()`/`renderSearchPanel()`) — this content is long-form prose and needs its own scrollable screen with a real back button.
- `topbar("ℹ️", "#home")` — no tint argument. The body background must fall back to the default `--bg` cream, not a vivid type color.
- Do **not** touch the existing gear/search buttons, panels, or any other route's behavior — this is a pure addition.
- No Python/pipeline changes, no `pytest` additions — frontend-only. Verification is live-browser only, per house rule ("green tests are not enough").
- Any change to `style.css` requires a `python3 build.py` run before merge so `sw.js` gets a fresh precache version stamp (`index.html` is not touched by this plan, but `style.css` is, which is the trigger either way).
- This is a real user-visible feature, so its release PR needs a **minor** version bump (`python3 bump_version.py minor`) — this depends on `bump_version.py` existing on `develop`, which lands there via the separate `docs/superpowers/plans/2026-08-11-version-bump-enforcement.md` plan (being executed in parallel). **Before starting Task 2 of this plan, confirm `bump_version.py` exists on `develop`** (`git show develop:bump_version.py >/dev/null` or check the file directly after a `git pull`) — if it doesn't yet, wait for that plan's Task 2 to land, since Task 2 of this plan can't complete its version bump without it.
- Git flow: feature branch off `develop`, PR-merge into `develop`, then a release PR `develop` → `master`. `develop`/`master` both have GitHub branch protection as of today (PR + 1 required approval, no direct push, no force-push, no deletion) — self-approval is impossible on this solo repo, so every merge uses the repo-owner's admin-bypass option, and **every merge needs the human partner's explicit chat confirmation first**, into `develop` as well as `master`.
